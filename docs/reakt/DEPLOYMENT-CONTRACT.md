# Provider-neutral deployment protocol: deterministic core

The current single-ConfigMap history backend is rejected for production scalability. Its replacement is being decided; the state-machine and evidence requirements below remain applicable.

`deploy` is the trusted deployment planner and transition reducer. It does not obtain credentials, run hooks, contact Kubernetes, verify signatures, or perform mutations. The `platform` executor runs this protocol with protected Kubernetes state and short-lived credentials; `reakt deploy` verifies the release before invoking it. The protocol has no cloud-provider dependency.

Managed-resource creation and reconciliation support Server-Side Apply only, with strict server validation and a stable domain field manager. There is no client-side apply, merge-patch, strategic-merge-patch, full-object replacement or delete/recreate fallback. Force defaults to false. `defineDomain({ force })` supplies the controller default and `manage(resource, { force })` overrides it per resource. Compilation records the effective resource setting and derives an exact `force-apply:<Kind>/<namespace>/<name>` risk that the independent platform ceiling must accept. Force uses SSA ownership takeover while retaining strict validation and UID/resourceVersion preconditions; it never enables a replacement or deletion fallback. Explicit lifecycle deletion remains UID/resourceVersion-preconditioned. Protected protocol records use conditional state updates to serialize transitions; these are deployment coordination, not an alternative resource reconciliation engine.

The public boundary is `plan_transition(&DeploymentRequest) -> Result<TransitionPlan>`, `begin(&TransitionPlan, executor_id) -> Result<TransitionRecord>`, and `advance(&TransitionPlan, &TransitionRecord, expected_revision, executor_id, Event) -> Result<TransitionRecord>`. All serialized records deny unknown fields and use camelCase. The output is a model-level plan, never a claim that a deployment was executed.

A required `registry.generationHistory` binds the complete, append-only allocation history to domain, cluster, the active generation, and an opaque CAS revision. The supplied previous generation must match that protected active pointer. Each allocation records generation ID, ServiceAccount name, transition ID, artifact digest, and IR digest. Failed, reserved, and retired generations remain allocated forever. The next generation, ServiceAccount, and transition ID must never appear in that history. Prior-generation build membership must match its historical allocation. The plan emits `generationReservation` for atomic reservation alongside claims before staging. Missing history fails parsing; the trusted adapter must prove completeness and perform the actual CAS.

A `GenerationPlan` combines `{generationId, artifactDigest, compiled}`. Build/artifact identity and generation identity remain separate. Generation IDs must be new even when the build is reused for rollback. `DeploymentRequest` supplies a transition ID, optional prior generation, next generation, separately supplied runtime and cleanup ceilings, a protected registry snapshot with complete generation history, and runtime observations. Only the protected registry plus the approved prior/current plans authorize lifecycle decisions. Runtime observations cannot add targets or grant deletion authority.

Protected claims identify `{apiGroup, resource, namespace, name}` independently of API version. Their domain, generation, transition, state and observed UID come from trusted deployment control state. New targets require unclaimed identities. Existing claims are accepted only when they match the exact prior approved generation and domain. Foreign, reserved or inconsistent claims block planning. Explicit adoption requires an operator approval from the separately administered `reakt-platform-intents` namespace. The approval binds the transition, generation, release, object UID/resourceVersion, prior managed fields, permitted apply payload and deletion policy. The executor rereads the approval and object and performs a strict non-force SSA dry-run before reservation. Signed-candidate live runs have verified non-force adoption of an existing object and preservation of its UID through upgrade. Transfer remains rejected pending a qualified source-suspension and held-claim executor.

The authoring `prune` default resolves to `delete` when true and `orphan` when false; an explicit resource `deletionPolicy` overrides it. These defaults are resolved into each resource’s approved plan, not interpreted from the new controller configuration during cleanup. Removed resources inherit their prior approved deletion policy. `orphan` produces a release-only cleanup item. `delete` produces a named cleanup item with UID-preconditioned deletion when protected claims contain a known UID. Without a trusted UID it permits only GET and completion on absence; a present object blocks cleanup. Runtime inventory cannot fill a missing trusted UID. Cleanup get/delete capabilities are separate from steady-state capabilities and require explicit platform-ceiling entries. `cleanup_decision(plan, record, identity, claim, live)` revalidates the plan and durable event history, requires phase `Cleaning`, resolves the target from the plan, and requires a `Releasing` claim for the exact domain, prior generation, UID, and current transition. The cleanup executor must reread the live object and protected claim before issuing any delete; UID mismatch blocks, absent objects permit completion, and unknown finalizers remain untouched.

The reducer advances `Planned -> Staged -> Quiesced -> Activated -> Cleaning -> Committed`. Every advance requires matching executor ownership, expected record revision, and exact plan digest. Retries of an already recorded event are idempotent. An event ID reused with different evidence fails. Out-of-order events fail.

Every pre-activation `Resume` returns to `Planned` and increments `verificationEpoch`. New staging, quiescence, and activation evidence must bind that epoch; previously used registry-CAS, process-termination, or access-revocation receipts cannot be relabeled and reused. A block after activation or during cleanup cannot use this resume operation; it needs a separately qualified recovery transition.

Staging evidence identifies the distinct next-generation ServiceAccount and has no authority to activate it. Quiescence requires an explicit adapter-issued evidence record for old process termination and obsolete-access revocation, including environment qualification and executor identity. Missing or uncertain evidence blocks activation. A Pod deletion/force deletion, lease expiry, wall-clock timeout, or annotation is not termination evidence. Initial installation uses an explicit no-previous-generation case rather than fabricated termination evidence.

Only after quiescence can activation be recorded. Cleanup completion requires receipts for every planned item, tied to the authorized UID and outcome. Delete receipts cannot report an orphan as deletion, and unresolved finalizers cannot report completed deletion. Commit requires obsolete-identity retirement evidence and retains the complete plan/audit references.

Executor takeover is deliberately unsupported. A crashed executor resumes with the same recorded identity and transition revision. A future takeover API must establish that the prior executor cannot continue; expiration alone cannot do so. The Kubernetes adapter implements conditional protected-state updates using resourceVersion and retains records across process death. This core's integer revision is a model CAS predicate, not a replacement for Kubernetes CAS.

The release verifier enforces provenance/signatures and digest-bound OCI integrity; the platform adapter enforces policy identities, bounded credentials, protected CAS and API UID preconditions. The generation proxy provides the writer-quiescence boundary. Exact Reakt Role checks do not establish total effective authority in the presence of additive platform RBAC. Full lifecycle and failure-injection qualification, production workflow integration, operational recovery and independent final review remain release gates; see STATUS.md for current evidence.
